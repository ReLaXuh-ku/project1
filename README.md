# Пошаговая Тактическая Игра (Консольная Лабораторная Работа)

Реализация пошаговой тактической мини-игры на C++ с использованием объектно-ориентированного программирования (ООП), паттернов проектирования и строгим управлением динамической памятью.

---

## 1. Архитектура проекта и структура классов

Проект построен по модульному принципу. Взаимодействие объектов организовано через инкапсулированные компоненты-характеристики и полиморфный интерфейс базового класса.

### Текстовая диаграмма классов (Class Diagram)
+-------------------------------------------------+
|                    attributes                   |
| (Health, Armor, Attack, AttackRange, Speed)    |
+-------------------------------------------------+
|
v (композиция)
+-----------------------------+
|       Абстрактный Unit      |
+-----------------------------+
|
+--------------------------+--------------------------+
|                          |                          |
v                          v                          v

(Bruiser, Samurai)        (Soldier, Mage)           (Healer, Cannoneer)

+-----------------------------+

+-----------------------------+
|          GameField          | <---> [GameFieldIterator]
+-----------------------------+
### Описание компонентов:
* **Классы-компоненты (`attributes.h`):** Параметры `Health`, `Armor`, `Attack`, `AttackRange` и `Speed` выделены в отдельные сущности. Вся внутренняя логика (например, уменьшение урона на величину брони, предотвращение отрицательного здоровья) инкапсулирована внутри них. Базовый юнит агрегирует эти объекты.
* **Базовый класс `Unit`:** Абстрактный класс с чисто виртуальным методом `execute_action(Unit& target) = 0` и полиморфным методом глубокого клонирования `clone()`. Задаёт общие правила перемещения («крестом» по Манхэттену) и расчёта дистанции атаки (по Чебышёву).
* **Конкретные подтипы:** Разделены на три логических заголовочных файла (`MeleeUnits.h`, `RangedUnits.h`, `GlobalUnits.h`). Каждый класс переопределяет метод `execute_action` под свои игровые задачи (атака, лечение).

## 2. Обоснование выбора паттерна проектирования

В проекте применен порождающий паттерн проектирования **Фабричный метод (Factory Method)** в лице статического класса `UnitFactory`.

### Почему выбран именно этот паттерн:
1. **Изоляция и инкапсуляция:** Игровое поле (`GameField`) и главный цикл игры (`main.cpp`) ничего не знают о существовании конкретных классов `Bruiser`, `Mage` или `Healer`. Они оперируют только базовым указателем `std::unique_ptr<Unit>`. Это минимизирует зацепление (coupling) кода.
2. **Упрощение инициализации:** Конструкторы конкретных подтипов жестко зашивают дефолтные балансные параметры персонажей (HP, броню, урон). Фабрика скрывает этот громоздкий процесс создания. Вызов сводится к лаконичному `UnitFactory::create_unit(Type, Position)`.
3. **Масштабируемость:** При добавлении нового типа юнита (например, Лучника) не нужно менять логику игрового поля или функции ввода. Достаточно расширить `enum` и дописать одну ветку `case` в фабрике.

## 3. Реализация кастомного итератора

В соответствии с требованиями, для обхода объектов контейнера `std::vector<std::unique_ptr<Unit>>` внутри класса `GameField` с нуля написаны собственные классы итераторов: **`GameFieldIterator`** (для чтения-записи) и **`ConstGameFieldIterator`** (для инспекции в константных методах).

### Принцип работы:
* Итераторы инкапсулируют внутри себя стандартный итератор вектора `current`.
* Перегружен оператор `++` для переключения на следующего бойца.
* Перегружен оператор `!=` для проверки окончания массива (совместимость с циклами `for-each`).
* Перегружен оператор `*` с применением **двойного разыменования (`**current`)**. Первая звёздочка извлекает умный указатель `unique_ptr` из итератора вектора, вторая — извлекает ссылку на сам чистый объект `Unit&`.

### Использование в коде (Пример из отрисовки панели):
```cpp
size_t target_index = 0;
for (auto inner_it = begin(); inner_it != end(); ++inner_it)
{
    // Итератор прозрачно возвращает объект Unit&, у которого берутся координаты
    if (display_index != target_index && u.can_attack((*inner_it).get_position()))
    {
        targets += std::to_string(target_index + 1) + " ";
    }
    target_index++;
}
```

## 4. Демонстрационные игровые сценарии

### Сценарий 1: Успешный тактический маневр и атака
1. Игрок выбирает Самурая (Юнит 2) с текущей позиции `(0, 4)`. У Самурая скорость перемещения `2`.
2. Игрок вводит команду направления `D` (вправо). Координаты меняются на `(2, 4)`. Ошибка не возникает, перемещение успешно вносится в Журнал действий.
3. В фазу действия Игрок выбирает того же Самурая и заявляет атаку по Магу бота (Юнит 5), стоящему на соседней клетке `(3, 5)`. 
4. Расстояние по Чебышёву равно `max(|2-3|, |4-5|) = 1`, что соответствует `Range = 1` Самурая. Наносится урон, броня цели снижает его, итоговое HP Мага уменьшается, Журнал фиксирует событие.

### Сценарий 2: Попытка нарушения правил и откат системы (Валидация)
1. Игрок выбирает Брузера (Юнит 1) на позиции `(0, 1)` и пытается сдвинуть его на клетку `(0, 4)`. Скорость Брузера равна `1`.
2. Система рассчитывает пройденный путь по Манхэттену: `|0-0| + |1-4| = 3`. Это больше доступной скорости юнита.
3. Происходит **полный откат действия без потери хода**. На экран выводится предупреждение: `ОТКАТ ХОДА: Недостаточно скорости или попытка пойти по диагонали! Попробуйте снова.`
4. Игрок вводит корректную команду, игра продолжается.

### Сценарий 3: Защита от наложения объектов
1. Игрок пытается передвинуть Солдата на клетку, где уже физически стоит Самурай команды игрока.
2. Метод `move_unit_by_index` сканирует массив координат через внутренний цикл. Обнаруживается совпадение.
3. Ход блокируется с пояснением `Эта клетка уже занята другим бойцом!`. Юниты не пропадают с поля и не стирают друг друга.

## 5. Таблица соответствия критериям оценки

| Критерий ТЗ | Реализация в проекте | Локация в коде |
| :--- | :--- | :--- |
| **Абстрактный класс** | Класс `Unit` содержит чисто виртуальный метод `execute_action` и виртуальный деструктор. Создание чистого `Unit` невозможно. | `Unit.h` |
| **Инкапсуляция параметров** | Характеристики вынесены в отдельные классы-обертки. Изменение значений идет через строгие методы контроля знака. | `attributes.h` |
| **Правило пяти (Rule of Five)** | Реализованы вручную: деструктор, конструктор копирования, оператор присваивания копированием, конструктор перемещения, оператор присваивания перемещением. | `GameField.h`, `GameField.cpp` |
| **Глубокое копирование (Deep Copy)** | Конструктор копирования поля использует полиморфный виртуальный метод `.clone()` для создания точных клонов в куче. | `GameField.cpp`, файлы подтипов |
| **Кастомный Итератор** | Созданы классы `GameFieldIterator` и `ConstGameFieldIterator` с перегрузкой операторов `++`, `*`, `!=`. | `GameField.h` |
| **Порождающий паттерн** | Паттерн Фабричный метод (`UnitFactory`) создает полиморфные указатели по `enum` типу. | `UnitFactory.h`, `UnitFactory.cpp` |
| **Защита от сбоев ввода** | Реализована функция `clear_input()`. Строковые и некорректные вводы символов направления (`"dd"`) полностью фильтруются. | `main.cpp` |
